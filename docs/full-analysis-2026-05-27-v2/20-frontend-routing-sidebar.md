## 1. Route inventory (verified count)

### 1.1 How routes are wired

Routes are declared as `[path, Component]` tuples in 10 group files (`src/routes/*.tsx`). Each file `export const FOO_ROUTES: [string, React.ComponentType][] = […]`. `routes/AppRouter.tsx` imports every group and renders one `<ModuleGroup>` per group:

```tsx
// AppRouter.tsx:97–122
{/* ── Module groups ── */}
<ModuleGroup roles={ALL_AUTHENTICATED}  routes={ANALYTICS_ROUTES}    />
<ModuleGroup roles={HR_ROLES}           routes={HR_ROUTES}           />
…
<ModuleGroup roles={ALL_AUTHENTICATED}  routes={STUB_ROUTES}            />
```

`ModuleGroup` (`routes/ModuleGroup.tsx:17–39`) does its own path-pattern test before mounting:

```tsx
const isActive = (Array.isArray(routes) ? routes : []).some(([pattern]) => {
  const regStr = '^' + pattern
    .replace(/:[^/]+\*/g, '.*')
    .replace(/:[^/]+/g, '[^/]+') + '$';
  return new RegExp(regStr).test(location);
});
if (!isActive) return null;
return (
  <RoleRoute roles={roles}>
    <Switch>
      {(Array.isArray(routes) ? routes : []).map(([path, Component]) => (
        <Route key={path} path={path}>
          <ErrorBoundary>
            <Suspense fallback={<PageLoader />}><Component /></Suspense>
          </ErrorBoundary>
        </Route>
      ))}
    </Switch>
  </RoleRoute>
);
```

Important consequence: a 403 caused by a failed `RoleRoute` check only fires when at least one pattern in the group matches. If a user opens a path that exists in some _other_ group whose role they don't have, the group is short-circuited and the 404 `<NotFound />` in `AppRouter.tsx:199` is rendered instead. Permission-denied paths therefore look identical to non-existent paths from outside.

## 4. MES role guard

Round 1 said: "MES routes guarded by `IOT_ROLES` not `PRODUCTION_ROLES`" with the citation `AppRouter.tsx:101`. Verifying current line 110:

```tsx
// AppRouter.tsx:108–114
<ModuleGroup roles={PRODUCTION_ROLES}   routes={PRODUCTION_ROUTES}   />
<ModuleGroup roles={DIRECTOR_ROLES}     routes={DIRECTOR_ROUTES}     />
<ModuleGroup roles={PRODUCTION_ROLES}   routes={MES_ROUTES}          />
<ModuleGroup roles={QC_ROLES}           routes={QC_ROUTES}           />
<ModuleGroup roles={DESIGN_ROLES}       routes={DESIGN_ROUTES}       />
<ModuleGroup roles={MRO_ROLES}          routes={MRO_ROUTES}          />
<ModuleGroup roles={IOT_ROLES}          routes={IOT_ROUTES}          />
```

**MES is guarded by `PRODUCTION_ROLES`**, not `IOT_ROLES`. Round 1's claim is wrong.

For completeness, `routes/roleConstants.ts` shows:
```ts
export const PRODUCTION_ROLES = ['production', 'production_manager', 'pp_manager', 'admin', 'manager'];
export const IOT_ROLES        = ['production', 'production_manager', 'admin', 'manager'];
```
`IOT_ROLES` is a strict subset of `PRODUCTION_ROLES` (it lacks `pp_manager`). So even if MES had been guarded by `IOT_ROLES` the practical effect would have been narrow (only `pp_manager` would be locked out of MES). Either way, current code is correct.

No `React.lazy` retry/error wrapper — the standard `Suspense fallback={<PageLoader />}` is used everywhere (`ModuleGroup.tsx:32`, `AppRouter.tsx:92,182,189,194`, `App.tsx:76,80,84,88,92,96,103,121`).

### 6.2 Special-case eager imports in `App.tsx`

`App.tsx:25` imports `Login` **eagerly** (`import Login from "@/pages/Login"`), not via `lazy()`. This forces `Login.tsx` and its transitive imports into the initial bundle so the login screen renders without a flash of `<PageLoader />`. All other public pages (`OTPVerify`, `IoTTablet`, `AIInterviewPublicPage`, `HRCapitalPublicTest`, `TelegramMiniApp`, `PosMonitorApp`, `ChatPageFull`) are lazy.

### 6.3 What does NOT get code-split

- Routes from the 10 module files share the route-tuple metadata (paths + lazy refs) at the top of each file, so importing `AppRouter.tsx` pulls in 10 modules' worth of `lazy()` thunks. The thunks themselves are tiny (≈100 bytes each) but they import role constants, icons, etc.
- `roleConstants.ts` is a single file pulled by `AppRouter.tsx` and `ModuleGroup.tsx`. Small and fine to bundle eagerly.

### 6.4 PageLoader

`PageLoader` (`components/PageLoader.tsx`, not inspected in detail) is used as the universal `Suspense` fallback. It is *not* lazy itself (not in the lazy-import list) — eagerly bundled.

### 6.5 Vite chunk hints

No `import(/* webpackChunkName */ … )` or Vite `/* @vite-ignore */` directives appear in the route files (grep returned no hits). Vite's default chunking will assign one chunk per `lazy(() => import())` call, producing ~340 chunks at build time. For an enterprise SPA this is on the heavy side but defensible given the role-gated module structure.

## 7. Layouts & route nesting

### 7.1 Layout layers

Wouter does not support nested `<Route>` declarations. Layouts are imposed by wrapping the router output. The hierarchy is:

```
App.tsx
└── <ErrorBoundary>
    └── <WouterRouter base={BASE_URL}>
        └── <QueryClientProvider>
            └── <AuthProvider>
                └── <LanguageProvider>
                    └── <ErpThemeProvider>
                        └── <TooltipProvider>
                            └── <MainApp>
                                ├── (location === "/login") → <Login />
                                ├── (location === "/otp-verify") → <Suspense><OTPVerify/></Suspense>
                                ├── (location === "/iot/tablet") → <Suspense><IoTTablet/></Suspense>
                                ├── (startsWith "/ai-interview/") → <Suspense><AIInterviewPublicPage/></Suspense>
                                ├── (startsWith "/public/hrc-test/") → <Suspense><HRCapitalPublicTest/></Suspense>
                                ├── (startsWith "/mini-app") → <Suspense><TelegramMiniApp/></Suspense>
                                ├── (startsWith "/pos-monitor") → <Suspense><PosMonitorApp/></Suspense>
                                ├── (= "/chat" || starts "/chat/") → <PrivateRoute><ChatSocketProvider><Suspense><ChatPageFull/></Suspense></ChatSocketProvider></PrivateRoute>
                                └── (default) → <PrivateRoute><ChatSocketProvider><AppShellModern><Suspense><AppRouter/></Suspense></AppShellModern><ChatWidget/></ChatSocketProvider></PrivateRoute>
```

### 7.2 Layout assignment by route

| Route family | Layout shell | Source |
|---|---|---|
| All 449 module-group routes | `AppShellModern` (top bar + module sidebar) | `App.tsx:114` |
| `/chat`, `/chat/admin`, `/chat/*` | None — full-bleed `ChatPageFull` inside `ChatSocketProvider` | `App.tsx:99–109` |
| `/login`, `/otp-verify` | None — public auth pages | `App.tsx:70–77` |
| `/iot/tablet` | None — kiosk full-screen | `App.tsx:79` |
| `/ai-interview/:id`, `/public/hrc-test/:id` | None — public links | `App.tsx:83–89` |
| `/mini-app/*` | Telegram mini-app shell (provided by `TelegramMiniApp`) | `App.tsx:91` |
| `/pos-monitor/*` | `PosLayout` (POS-specific shell) | `pos-monitor/PosMonitorApp.tsx:39, 110–118` |
| `/order-workflow` | `AppShellModern` (reaches `AppRouter` first) | `AppRouter.tsx:180` |
| `/` | `AppShellModern` → `DirectorDashboard` (RoleRoute gated to `DIRECTOR_ROLES`) | `AppRouter.tsx:91–95` |

### 7.3 Provider stacking

`AppShellModern` routes get:
1. `PrivateRoute` (auth check)
2. `ChatSocketProvider` (websocket for unread badge)
3. `AppShellModern` (sidebar/header)
4. `Suspense` → `AppRouter` → `ModuleGroup` → `Switch` → `Route` → `ErrorBoundary` → `Suspense` → `Component`

That is **5 wrappers and 2 Suspense boundaries** between the auth check and the page. Each wrapper is cheap but the double `<Suspense>` means a route navigation can show two different fallbacks back-to-back (outer `App.tsx:121` fallback while `AppRouter` resolves, then inner `ModuleGroup` fallback while the page chunk loads). In practice both are `<PageLoader />` so the user sees the same spinner.

### 7.4 No declarative nesting

There is no use of wouter's `<Route nest>` or React Router-style `<Outlet>`. Hierarchical UIs (e.g. tab-style pages) are implemented inside the page component using `useLocation` + manual tab state. The `*Extended` pages (§5.1) all do this — opening `/mes/oee-monitor` vs `/mes/reason-log` lands in the same component, which then reads `useLocation` to flip its internal state.

### 8.2 Auth model — entirely separate from the main app

`PosMonitorApp.tsx:56–71`:

```ts
function isAuthenticated(): boolean {
  try {
    const sess = localStorage.getItem("pos_session");
    if (!sess) return false;
    const parsed = JSON.parse(sess) as { token?: string };
    if (!parsed.token) return false;
    const parts = parsed.token.split(".");
    if (parts.length !== 3) return false;
    const payload = JSON.parse(atob(parts[1])) as { exp?: number };
    if (payload.exp && payload.exp * 1000 < Date.now()) {
      localStorage.removeItem("pos_session");
      return false;
    }
    return true;
  } catch { return false; }
}
```

- Token stored in `localStorage["pos_session"]`, not the cookie/session that the main app's `useAuth` reads.
- JWT expiry decoded client-side (`atob(parts[1])`) — no signature verification.
- A POS user logging in does **not** authenticate to the main ERP and vice versa. This is intentional for the POS Telegram-mini-app use case but worth documenting.

`AdminGuard` (`PosMonitorApp.tsx:91–108`) gates `/pos-monitor/admin` to a hard-coded set:

```ts
const POS_ADMIN_ROLES = new Set(["pos_manager", "admin", "super_admin", "finance_head"]);
```

These role strings are different from the main app's `roleConstants.ts` (`finance_head` does not exist there; `cfo` and `finance_manager` do). The two role systems are not coordinated.

### 8.3 Layout

`PosLayout` (`pos-monitor/layout/PosLayout.tsx`) wraps every authenticated POS route. `PosLogin` is bare. The catch-all `/pos-monitor/:rest*` redirects unknown sub-paths to `/pos-monitor` (the dashboard) — so a typo doesn't show the main-app's NotFound.

### 8.4 Telegram WebApp init

`PosMonitorApp.tsx:122–128` calls `initTelegramWebApp()` once on mount. If the page runs inside Telegram, `document.documentElement.setAttribute("data-tg-app", "true")` is set, letting the POS CSS theme adapt. This means POS Monitor is designed to run both as a standalone web page and as a Telegram WebApp.

### 8.5 Lazy loading

All 27 POS pages are `lazy(() => import(...))` (`PosMonitorApp.tsx:12–39`). The shared `PosLayout` is also lazy. The fallback is `<PosLoader>` (in-file, lines 41–54), a styled placeholder with `📦` emoji and a "POS Monitor yuklanmoqda" label, **not** the main app's `PageLoader`. Visual continuity between main ERP and POS is intentionally broken.
