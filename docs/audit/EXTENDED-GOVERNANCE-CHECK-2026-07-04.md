## Top 5 highest-leverage fixes

Ranked by how many other principles/modules each touches, not by raw severity alone:

1. **Fix the two live silent-catch-swallow bugs (A5)** — `drizzle-lead.repo.ts` `findByCompanyId`/`findByStatus` and `drizzle-hr-leave.repo.ts` `save360Feedback`, both returning `{ok:true,...}` on real DB errors. Highest leverage because `save360Feedback`'s sole caller is wired live off `mes-completed.listener.ts` — the MES→HR golden-thread event flow project memory repeatedly treats as the system's backbone integration test. It's also a precondition for trusting every other fix in this audit: if a repo can lie about success, A7's role-gated approve/reject flows and A4's controller-embedded writes become impossible to verify as actually-working even after they're individually fixed.
2. **Index the new canonical org-card FK columns (A6)** — `employees.org_department_id`, `employees.org_function_id`, `org_functions.razryad_level_id`. These sit at the center of the active VIZYON org-card build (per project memory) and compound directly with B14 (employees has zero audit-ownership columns) and B15 (employees' classification columns are 100% NULL) — all three point at the same table being under-instrumented for the exact restructuring work in flight. Also the actual root cause behind several of A2's unbounded-select findings (sequential scans instead of indexed lookups).
3. **Consolidate materials/products fragmentation (B10)** — repoint `materials`, `products`, `raw_materials`, `product_masters` onto `material_cards` the same way `mm_materials` was already converted to a VIEW on 2026-06-22. This is connective tissue under B9 (intelligent-key anti-pattern only cleanly fixable with one canonical table), B12 (nullable-constraint drift exists partly because finance costs and WMS/POS stock read two different tables for the same entity), and A2 (unbounded selects compounded by cross-table duplication). The existing VIEW-migration precedent makes this the most executable of the five, not just the most theoretically valuable.
4. **Standardize the repository-layer naming split (A1)** — 308×`.repo.ts` vs 263×`.repository.ts` → the documented canonical `.repository.ts`, done as a scripted rename. Low risk, high leverage for tooling: any future lint/codemod written to catch A2/A3/A4 violations at the repository layer currently has to match two glob patterns and will silently miss half the codebase otherwise.
5. **Close the `mini-app.controller.ts` approve/reject authorization gap (A7)** — add role/permission checks to `pos-request.service.ts`'s `approveRequest()`/`rejectRequest()`, removing reliance on the class-level `@Public()` bypass. The one clear must-fix-now security hole in this audit, and it intersects directly with B14 (no audit trail exists to reconstruct who approved what) and A5 (no guarantee the write path reports failure honestly) — fixing authorization alone here would leave a fixed-on-paper but still-unauditable control.

## ABAP-specific items that do not apply to this stack

| ABAP/SAP item | Why it doesn't apply here | What replaces it |
|---|---|---|
| **Transport Requests** (change-transport system moving config between dev/QA/prod landscapes) | No ABAP-style client-dependent config layer exists to transport separately from code — there is one shared PostgreSQL schema and a monorepo that ships together. There is no "config-only" transportable unit distinct from source, so the concept (which exists specifically because ABAP config lives outside normal source control) has no analogue to silently drop. | Git commits/branches carrying code AND schema changes together, versioned SQL migration files (e.g. `mm-materials-unify-view-2026-06-22.sql`) applied idempotently and tracked in-repo, plus CI gating what merges to the shared branch. |
| **`AUTHORITY-CHECK`** (SAP's inline per-object authorization statement) | The mechanism is real, not absent — this audit's A7 findings directly exercised it. The difference is the failure mode, not the existence: `AUTHORITY-CHECK`-style deny-by-default doesn't map onto this framework's guard design, which fails OPEN when no decorator is present. | NestJS global guards (`JwtAuthGuard`/`RolesGuard`/`SodGuard`/`PermissionGuard`) plus per-route `@Roles(...)`/`@RequirePermission(...)` decorators — declarative, evaluated by a guard rather than inline in procedural code. A7's real findings (mini-app approve/reject, gofra-conversion mutations) are gaps in decorator coverage, not evidence the mechanism is missing. |
| **`sy-subrc`** (ABAP's implicit after-every-statement return-code system field) | There is no implicit, ambient "did the last statement succeed" flag anywhere in this stack. | The codebase's own explicit Result/Ok/Err pattern plus NestJS `HttpException` subclasses for the transport layer — every DB call or service method must explicitly return or throw a typed result the caller inspects. This audit's A5 finding (two repos manufacturing a fake `{ok:true}` inside a catch block) is a **violation** of this codebase's own explicit-Result discipline, not evidence the discipline is missing — and arguably worse than `sy-subrc`, since it actively lies about the result rather than merely requiring the caller to remember to check an ambient flag. |
