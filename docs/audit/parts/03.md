### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **TWO-WORLDS confirmed**: `sales_orders` (12 rows, all ow_* FKs, SD module writes) vs `orders` (0 rows, no FK children, no SD writer). `sd_sales_orders` = VIEW over `sales_orders`. `sd_orders` = VIEW over `orders`. The `orders` table is structurally different: it has `product_id`, `quantity`, `tenant_id` (uuid), `manager_id`, `production_order_id` columns that `sales_orders` lacks; `sales_orders` has `overall_status`, `design_flag`, `sample_flag`, `tech_*_approved`, `advance_required`, `advance_status`, `created_by` (uuid) that `orders` lacks. No FK bridges the two tables.

- **GREEN-LIE: sales.service.ts:42** — `GET /api/sales/forecast/accuracy` returns hardcoded `{accuracy_percent: 78.5, periods: [...January/February/March...]}` — no DB access at all. FE calling this gets stale mock data.

- **GREEN-LIE: sales.service.ts:69-74** — `GET /api/sales/forecast/history` always returns `{history: [], limit: N}` — no DB read. Permanently empty.

- **DUPLICATE route: sd-orders.controller.ts:206** — `PUT /api/sd/orders/:id/status` is a verb-alias of `PATCH /api/sd/orders/:id/status` — both dispatch the exact same `UpdateOrderStatusCommand`. Not a business-logic dup, but adds surface area.

- **FE drift — cancel route missing**: `SDSalesOrders.tsx:188` calls `PATCH /api/sd/orders/:id/cancel` with `{reason}`. There is NO such route in `sd-orders.controller.ts` — the controller has no cancel endpoint. The `DrizzleSdOrdersRepository.cancel()` method exists but is only reachable through `OrdersService.cancel()` which is not wired to any controller endpoint in the SD slice (no `@Delete` or `@Patch` cancel handler). FE cancel button will always return 404.

- **Type mismatch (created_by)**: `sales_orders.created_by` is `uuid` in the live DB (confirmed via information_schema), but `CreateOrderHandler` passes `command.createdBy` (an integer user id from JWT) as `String(createdBy)` → `DrizzleSdOrdersRepository.create()` line 58. Integer strings like `"42"` are not valid UUIDs — inserts will fail with a cast error unless PostgreSQL coerces them (unlikely; PostgreSQL will throw `invalid input syntax for type uuid`).

- **ORPHAN tables**: `sd_order_timeline`, `order_status_logs`, `order_approvals`, `order_commissions`, `order_costings` — all exist in the DB with 0 rows and no writer found in any SD module file.

- **Domain events outbox 0 rows**: `domain_events` table exists but has 0 rows. The outbox publisher (`OutboxRepository.insertBatch()`) runs inside the CreateOrder transaction — if no orders have been created since DB reset, the 0-row count is expected (build stage). However if any order was created and the outbox row was missing, that would indicate the transaction failed silently.

- **sd_order_departments.order_id FK verified**: `ow_cliches.order_id`, `ow_material_requirements.order_id`, `ow_molds.order_id`, `ow_shipping_requests.order_id`, `ow_tech_cards.order_id`, `sales_order_items.sales_order_id`, `sd_order_departments.order_id` — all 7 FKs confirmed pointing to `sales_orders(id)` via information_schema. Phase-4 fan-out is properly anchored.

- **orders table — no FK children, no listener**: The `orders` base table (sd_orders / ow_orders / pp_orders VIEW source) has 0 rows and zero FK references from any table. It is a structural dead end in the current codebase. PP module reads `pp_orders` (VIEW over `orders`), but since `orders` has 0 rows and no SD writer, PP has no data.

- **Missing pagination total for pending-advance**: `PendingAdvanceOrdersHandler` (pending-advance-orders.handler.ts:30) returns `total: result.data?.length || 0` — the total is the page size, not the full DB count. Pagination will be wrong for offsets > 0.

### 3-line summary

`sales_orders` (12 rows) is the canonical order table; `sd_sales_orders` is a passthrough VIEW over it; all 7 FK children (ow_* + sales_order_items + sd_order_departments) are properly anchored to `sales_orders`. The parallel `orders` table (base for `sd_orders`/`ow_orders`/`pp_orders` VIEWs) has 0 rows, no FK children, and no SD writer — it is a structural dead second world that starves the PP module. Two routes are green-lies (`GET /api/sales/forecast/accuracy` returns hardcoded data; `GET /api/sales/forecast/history` returns always-empty array), and the FE cancel button calls `PATCH /api/sd/orders/:id/cancel` which does not exist in any controller.
