### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **SCHEMA DRIFT — planned_start/planned_end vs planned_start_date/planned_end_date**: `drizzle-pp-production-orders.repo.ts:10` imports `productionOrders` from `@europrint/schemas` which resolves to `schema-compat-3.ts:30-31` defining columns `plannedStart`/`plannedEnd` (mapped to `planned_start`/`planned_end`). Live DB has NO `planned_start` or `planned_end` columns — only `planned_start_date`/`planned_end_date` (varchar) and `scheduled_start`/`scheduled_end` (timestamp). Any INSERT via `DrizzlePpProductionOrdersRepository.create()` will fail or silently use null for those dates.

- **TWO PRODUCTION-ORDER SCHEMAS**: `production_orders` is defined in THREE different places: `lib/db/src/schema/pp/pp-production.ts` (canonical, full schema), `apps/api/src/shared/db/schema-manufacturing.ts:64` (production_orders with different column set), and `apps/api/src/shared/db/schema-compat-3.ts:23` (productionOrders, minimal — planned_start/planned_end). The CQRS handlers import from `@shared/db` which resolves to `schema-manufacturing.ts`; `DrizzlePpProductionOrdersRepository` imports from `@europrint/schemas` (compat-3 stub). Two writers, two different column maps, same table.

- **MISSING FK — production_orders.sales_order_id**: Live DB shows zero FK constraints on `production_orders`. Column `sales_order_id` (integer) exists but no FK to `sales_orders.id`. The order→production bridge is FK-less. Confirmed via `pg_constraint` query returning empty.

- **TWO-WORLDS ORDER BRIDGE — orders vs sales_orders**: `orders.production_order_id` (integer) exists in live DB (confirmed). `sales_orders` has NO `production_order_id` column. The PP module's `CreateProductionOrderCommand` takes `soId` (sales_order_id) and writes it into `production_orders.sales_order_id`, but this links to `sales_orders` (12 rows) while `orders` (the base table for `pp_orders` VIEW, 0 rows) has its own separate `production_order_id` back-reference. The two order worlds are not reconciled.

- **TYPE MISMATCH — getById**: `get-production-order-by-id.handler.ts:25` calls `eq(production_orders.id, String(query.id))` — `production_orders.id` is `integer` in the live DB; casting query id to `String` when using eq() against an integer column may cause unexpected behavior or 0-row results.

- **FE URL MISMATCH**: `TechPPExtended.tsx:38` queries `/api/pp/production-orders` (with hyphen). The controller at `pp-orders.controller.ts:44` registers `@Controller('pp/orders')` — path is `/api/pp/orders`, not `/api/pp/production-orders`. FE call will 404 silently (shows empty array due to default `orders = []`). The `ppApi` in `lib/api/pp.ts:17` uses the correct `/api/pp/orders`, but the page component's direct query uses the wrong path.

- **ORPHAN — production_status_history, production_qc_checks, production_material_allocs**: Tables exist in live DB (0 rows) and in Drizzle schema but no API endpoint writes to them. History entries for status changes are not recorded. QC checks for production orders are not written.

- **DUPLICATE PATH — /api/production/orders vs /api/pp/orders**: Two separate GET-orders routes exist: `production-reports.controller.ts:81` (`GET /api/production/orders`) and `pp-orders.controller.ts:55` (`GET /api/pp/orders`). Both query `production_orders` table with similar logic but different column access (one raw SQL, one Drizzle ORM).

- **DEAD COLUMN REF — production.repository.ts:89**: `getOrder360Card` SQL references `po.operator_id` and `po.bom_header_id`. Neither column exists in live `production_orders` table (confirmed by column list). Will silently return NULL for those joined fields.

- **NO WRITER FOR orders.production_order_id BACK-REFERENCE**: The `orders` table has `production_order_id` column but no code sets it when a production order is created. The golden-thread bridge (order→production order→factory) is structurally incomplete: PP can read `soId` from the command but does not write back to `orders.production_order_id`.

- **AdvanceApprovedListener trigger 7 gap**: `advance-approved.listener.ts:26` calls `ppRepo.unlockPlanning(event.orderId)` which sets status to `'pending'`. But `unlockPlanning` uses `production_orders_int` (canonical Drizzle table) while `orderId` in the event is a `sales_orders.id` value, not a `production_orders.id`. There is no production order FK to `sales_orders.id`, so the UPDATE will silently affect 0 rows.
