### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **TWO-WORLDS — design creation split across two paths**: `POST /design` (design.controller.ts:112) uses `DrizzleDesignRepository.save()` which writes to `design_orders` with minimal fields (order_number=`DO-<timestamp>`, deal_id from salesOrderId). `POST /design/orders` (design.controller.ts:218) is a 501-STUB that rejects with NotImplementedException. Meanwhile `DrizzleDesignOrdersSvcRepository.create()` (design-orders-svc.repo.ts:48–54) is a third independent INSERT path into `design_orders` via the `@europrint/schemas` `designOrders` schema ref — never called from any controller. Three create paths, one table, zero coordination.

- **DUPLICATE route concept — GET /design vs GET /design/orders**: `GET /design` (design.controller.ts:77) returns paginated `{ items, total, page, limit }` via CQRS query → `DrizzleDesignRepository.findAll`. `GET /design/orders` (design-extended.controller.ts:33) returns `{ order: { id, orderNumber, productName, clientName, status, productType } }` via `DesignExtendedRepository.findOrdersList`. Both read `design_orders` but return different shapes. FE DesignOrders.tsx:80 calls `/api/design/orders` (extended), while DesignOrderDetail.tsx:67 also calls `/api/design/orders/:id` — but that path does NOT exist on DesignExtendedController (no `GET /design/orders/:id` endpoint). The FE will get a 404/500 for order detail.

- **FE-BE DRIFT — POST /design/orders is 501**: FE `DesignOrders.tsx:84` calls `POST /api/design/orders` with a rich form (clientName, productType, productName, brandName, quantity, etc.). BE `design.controller.ts:218` explicitly throws `NotImplementedException`. The form submission always fails with 501. Users cannot create design orders from the DesignOrders page.

- **FE-BE DRIFT — GET /design/orders/:id missing**: FE `DesignOrderDetail.tsx:67` queries `/api/design/orders/:id`. No such route exists. `DesignExtendedController` has `GET /design/orders` (list) but no by-id endpoint. `DesignController` has `GET /design/:id` but that's at a different path. Order detail page always fails.

- **GREEN-LIE — GET /design/templates**: `DesignExtendedRepository.findTemplates()` (design-extended.repository.ts:68–76) returns a hardcoded array of 5 items via `Ok([...])` — no DB table, no `design_templates` table exists. FE `DesignExtended.tsx:39` calls `/api/design/templates` and shows these fake values as real templates.

- **GREEN-LIE — POST /design/:id/verify**: `verifyDesign()` (design-extended.repository.ts:98–100) uses `Math.random()` for scores and passes/fails — completely fabricated, ignores designId, reads nothing from DB. FE `AIDesignGenerator.tsx:80` calls this and displays the random results as AI quality scores.

- **GREEN-LIE — POST /design/:id/mockup**: `generateMockup()` (design-extended.repository.ts:102–104) returns a fabricated local path `/mockups/<id>-<type>.png`. No actual file generation, no storage write. FE `AIDesignGenerator.tsx:104` calls this and shows the non-existent URL as a real mockup.

- **ORPHAN — LibraryService + LibraryRepository**: Files exist at `apps/api/src/modules/design/library/library.service.ts` and `library.repository.ts` with full CRUD for `design_library_items`, but neither is registered in `design.module.ts`. No controller calls them. The `design_library_items` table (0 rows) has a writer but it is unreachable at runtime.

- **ORPHAN — design_comments table**: Table exists in live DB (0 rows) but no reference in any `.ts` file in `apps/api/src`. No writer, no reader.

- **ORPHAN — design_order_revisions read but never written**: `DesignExtendedRepository.findOrderRevisions()` reads `design_order_revisions` but nothing in the codebase inserts revision rows. `GET /design/orders/:orderId/revisions` will always return [].

- **NO FK — design_orders.deal_id / design_orders.sales_order_id**: `design_orders` has both `deal_id` (integer) and `sales_order_id` (text) columns linking to sales. Zero foreign key constraints on either column (confirmed via information_schema). The `DrizzleDesignRepository.save()` writes `deal_id` (from salesOrderId cast to int) while also having a `sales_order_id text` column — two separate link fields for the same concept.

- **PHASE-4 DISCONNECT — ow_tech_cards vs design_orders**: The Phase-4 fan-out (sd-order-departments.repo.ts:61) creates `ow_tech_cards` rows when design dept is selected in an order. However, `design_orders` is the module's own table and is never linked to `ow_tech_cards`. Design dept jobs track status in `ow_tech_cards.status` (SD module), while the design module tracks work in `design_orders.status` — two parallel tracking systems for the same design work, no FK or sync between them.

- **SoDesignRequestedListener is no-op**: `SoDesignRequestedListener.handle()` (so-design-requested.listener.ts:22) only logs a message — no business logic, no writes. This is one of the 13+ zero-listener events noted in the transmission map.

### Vision link (which of 22 visions this serves, % built)

Design module serves Vision: "Design request from order" (order → manager selects depts → design dept gets fan-out job → designer works → approved design flows back). 

- Order creation → design_orders: ~60% (POST /design works and saves; but the richer POST /design/orders form is 501-stubbed)
- Status transitions (approve/reject/update): ~70% (REAL DB writes to both `design_orders` and `designs` tables, state machine enforced)
- AI design generation: ~40% (generates and saves variants to `designs` table, but verify=green-lie, mockup=green-lie)
- Design-to-order fan-out loop (Phase 4): ~20% — ow_tech_cards created by SD module but design module does not read/update it; the two tracking worlds are disconnected
- Revision history: ~5% (table exists, no writer)
- Templates: ~10% (hardcoded, not persisted)
- Library: ~0% at runtime (service written but not wired)

Overall: approximately **35% built** against the full vision.

### 3-line summary

The design core has real DB writes for the main CRUD path (POST /design creates in `design_orders`, approve/reject update `designs`) but contains 3 green-lies (templates hardcoded, verify and mockup return fabricated data), 1 critical 501-stub (POST /design/orders — the primary FE create form), and a missing GET /design/orders/:id route that breaks the DesignOrderDetail page. A two-worlds split exists between `design_orders` (design module's own tracking) and `ow_tech_cards` (Phase-4 SD fan-out for the design dept) with no FK or sync. LibraryService/Repository code is fully written but unreachable at runtime because it is not registered in design.module.ts.
