### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **Two-worlds: pos_printer_config vs pos_printer_configs** — Two separate physical tables for the same business concept. `pos_printer_config` (singular, 9 cols: printer_ip, printer_port, print_format) is used by the POS-module ORM path (pos-printer-config.repository.ts:9, lib/db/src/schema/pos-schema-v2.ts:690). `pos_printer_configs` (plural, 10 cols: ip_address, port, type, settings JSONB) is used by the WMS-barcode raw-SQL path (wms-barcode.controller.ts:64). Both tables exist in live DB, both have 0 rows. FE `PrinterSettingsTab.tsx:58` calls `/api/warehouse/printer-config` (plural table) but test-connection call at line 99 hits `/api/v2/pos/printer-config/:id/test` which reads from the singular table — if user creates a config via warehouse endpoint it will never be found by the test endpoint.

- **Duplicate test routes** — `POST /api/pos/printer-config/:id/test` (printer-config.controller.ts:69) and `POST /api/v2/pos/printer-config/:id/test` (pos-printer-config-v2.controller.ts:31) are identical in logic; the v2 controller exists only as an "alias" but routes to the same underlying service and same singular table. FE uses v2 path (PrinterSettingsTab.tsx:99).

- **GREEN-LIE: PATCH /api/warehouse/printer-config/:id** — wms-barcode.controller.ts:91-104 runs an UPDATE but returns `{ id: parseInt(id,10), updated: true }` unconditionally without checking rows affected or using RETURNING. If the id does not exist, the response is still `{ updated: true }`. Additionally the `isActive` field sent by FE (PrinterSettingsTab.tsx:90) uses camelCase `isActive`, but the PATCH body parsed with `PrinterConfigSchema.partial()` maps to `dto.active` (not `isActive`), so toggling active status silently does nothing.

- **FE-BE drift: isActive vs active** — FE `toggleActiveMutation` at PrinterSettingsTab.tsx:90 sends `{ isActive: boolean }` to PATCH `/api/warehouse/printer-config/:id`. The WMS controller parses with `PrinterConfigSchema` which maps `.active` (not `.isActive`), so the active-toggle mutation never updates `is_active` in `pos_printer_configs`. The Zod schema at wms-barcode.controller.ts:20 has `active: z.boolean().optional()` but FE sends `isActive`.

- **FE-BE drift: response shape for GET /api/warehouse/printer-config** — FE `PrinterSettingsTab.tsx:57` expects `{ configs: PrinterConfig[], active: PrinterConfig | null }` but WMS controller returns a raw array (`Row[]`) at wms-barcode.controller.ts:64. The FE destructures `configData?.configs` which will be undefined causing the table to render empty.

- **Orphan routes: mm_material_kits / mm_material_kit_items tables missing** — All routes under `/api/iot-enhanced/material-kits` (iot-enhanced.controller.ts:64-112) and `/api/iot/material-kits` (iot-material-kits.controller.ts:38-115) target `mm_material_kits` and `mm_material_kit_items` tables confirmed absent from live DB. Every call will throw a PostgreSQL relation-does-not-exist error. FE pages `WarehouseMaterialKits.tsx:38` (calls `/api/iot-enhanced/material-kits`) and `useIoTTablet.ts:105` (calls `/api/iot/material-kits/generate`) will always fail.

- **FE URL mismatch: WarehouseMaterialKits.tsx uses two different base paths** — line 38 calls `/api/iot-enhanced/material-kits` (GET list) but mutation at line 60 calls `/api/iot/material-kits/:id/prepare` and line 70 calls `/api/iot/material-kits/:id/ready`. This is consistent with having two controllers (`IotEnhancedController` and `IotMaterialKitsController`) for the same resource, but both target the missing `mm_material_kits` table.

- **material_kits vs mm_material_kits: two-worlds for material kits concept** — `material_kits` table exists in live DB (used by `/api/warehouse/material-kits` in wms-barcode.controller.ts); `mm_material_kits` table does not exist (targeted by IoT controllers). The IoT controller codebase (iot-enhanced.repository.ts:34) queries with JOINs against `production_orders` and `employees`, whereas wms-barcode simply inserts with hardcoded `order_id=0`. These represent two separate implementations of the same business concept, one of which is completely broken.

- **wms-barcode POST /api/warehouse/material-kits hardcoded order_id=0** — wms-barcode.controller.ts:135: `order_id` is hardcoded to `0` in the INSERT. The `material_kits.order_id` column exists but all created kits will have invalid order reference.

- **FE stub route /pos/printer-config** — StubRoutes.tsx:83 registers `/pos/printer-config` as a stub page. This is the sidebar-facing route. The real printer config UI lives in `PrinterSettingsTab.tsx` embedded in the barcode module, so the dedicated `/pos/printer-config` page remains a stub.

### Vision link (which of 22 visions this serves, % built)

This slice serves the **WMS/Warehouse operations** vision (thermal label printing, kit management for production floor) and the **POS Monitor** vision (printer hardware configuration for barcode printing at factory warehouse). Printer-config: ~40% built — CRUD exists on two parallel tables, test-connection works on one path, but FE-BE contract is broken (response shape, isActive field). Material-kits: ~20% built — `material_kits` table and WMS-barcode CRUD exist but the IoT-facing paths (the primary consumer) target a non-existent `mm_material_kits` table.

### 3-line summary

The slice has a critical two-worlds split: printer configuration is stored in two incompatible tables (`pos_printer_config` for the POS ORM path, `pos_printer_configs` for the WMS raw-SQL path) and the FE test-connection call crosses between them, always returning 404 in practice. Material kits exist in `material_kits` (WMS path, live) but all IoT-facing routes target `mm_material_kits` which does not exist in the live DB, causing runtime crashes on every kit create/list/update call from the WarehouseMaterialKits page. The PATCH printer-config endpoint is a green-lie (returns `updated: true` regardless of result and silently ignores the FE `isActive` field due to schema naming drift).
