### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **DEAD-LETTER LISTENER** — `PosGlAutoListener` at pos-gl-auto.listener.ts:35 listens for `PosMovementCompletedEvent` but the comment at line 18-21 (confirmed by grep) states no production code emits `pos.movement.data.completed` on either bus. The listener has never fired in production. The inline path in pos-movement-status.service.ts:203-226 is the actual active GL write path, making the listener fully redundant dead code.

- **TWO-WORLDS GL LOG** — `pos_gl_posting_log` (staging log, managed by GlPostingLogRepository) and `pos_gl_postings` (second posting table, managed by AutoGlPostingRepository) are both active writers but serve the same concept. The FE GlTab.tsx:59 and PosAdmin.tsx:59 call `/gl/pending` and `/gl/approve/:id` (pos_gl_posting_log path). The AutoGlPostingService writes to `pos_gl_postings` via `/wh-features/movement/:id/gl` — no FE component calls this POST route in the POS monitor. This is a genuine duplicate GL staging concept.

- **THREE-WORLDS LEDGER** — After Finance approval, `GlPostingLogRepository.postMovementToLedger` inserts into `entries` (canonical, pos-monitor.api.ts-connected). But the Finance module writes to `gl_journal_entries` + `gl_lines` (via drizzle-finance-accounting.repo.ts, drizzle-finance-ops.repo.ts). Three separate ledger tables exist in the live DB with 0 rows each: `entries`, `gl_journal_entries`, `gl_lines`. No FK or reconciliation bridge connects them.

- **GL ACCOUNT MISMATCH** — GL_PAIRS in pos-gl-auto.service.ts uses account codes like '2110', '6010', '1210', '9110' (not in CoA). The gl_account_mappings table uses different codes ('1010', '2010', '4000', '6000', '9010', '9500', '9810'). `postMovementToLedger` looks up accounts table by code from gl_account_mappings; those 7 of 7 present codes do match. But the GL_PAIRS hardcoded codes ('2110', '6010', '9110' etc.) used in the inline write path and the dead listener do NOT match accounts in the CoA — a mismatch between the two code sets that will cause silent WARN (no mapping found path) if the listener ever fires.

- **PROMOTION GAP (money mismatch)** — When Finance approves via `POST /api/pos/gl/entry/:id/approve`, `postMovementToLedger` is called which inserts a single-leg (debit+credit combined) entry into `entries`. The `gl_entries` JSONB in `pos_gl_posting_log` may contain 2-4 GL pairs but the promotion collapses them into one entry row (one debit_account_id, one credit_account_id, one amount). Multi-leg postings (e.g. EXTERNAL_IN has 4 legs: 2110 Dr, 6010 Cr, 1410 Dr, 2110 Cr) lose the intermediate legs during promotion. `gl-posting-log.repository.ts:146-153`.

- **APPROVAL → entries path broken conditionally** — `postMovementToLedger` queries `gl_account_mappings` first. `INTERNAL_TRANSFER` has no entry in `gl_account_mappings` (per seed SQL comment and confirmed by DB: only 6 rows, INTERNAL_TRANSFER absent). So approving an INTERNAL_TRANSFER movement writes to pos_gl_posting_log with status=POSTED but silently skips entries promotion with reason="no GL mapping for 'INTERNAL_TRANSFER'". gl-posting-log.repository.ts:133-134.

- **FE drift — getJournal path** — `glApi.getJournal()` in pos-monitor.api.ts:98 calls `/gl/journal` (GlController) which returns rows from `pos_gl_posting_log` where status=POSTED. These are log rows, not canonical `entries` ledger rows. The FE finance view is therefore showing the staging log, not the real GL ledger.

- **pos_gl_postings ORPHAN (no FE trigger)** — `AutoGlPostingService.postForMovement` writes to `pos_gl_postings`. The FE never calls `POST /api/pos/wh-features/movement/:id/gl`. The only trigger would be manual HTTP call. `pos_gl_postings` has 0 rows and no event or automatic caller. It is a parallel GL staging table with no integration into the approval or ledger promotion chain.
