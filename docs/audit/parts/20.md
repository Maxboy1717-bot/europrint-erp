### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **Two-worlds (critical):** The codebase splits "material kits" across two entirely separate table families:
  1. `material_kits` / `material_kit_items` — the CANONICAL Drizzle schema (`lib/db/src/schema/mm-batch-mgmt.ts:93,130`), exists in live DB, written by `/api/warehouse/material-kits` (wms-barcode.controller.ts)
  2. `mm_material_kits` / `mm_material_kit_items` — targeted by `iot-enhanced.repository.ts` (lines 34, 43, 60, 68, 83, 93) — these tables **do not exist** in the live DB. Every route under `/api/iot-enhanced/material-kits*` and `/api/iot/material-kits*` will throw a PostgreSQL "relation does not exist" 500 error at runtime.

- **FE calls wrong table via wrong prefix (critical):**
  - `WarehouseMaterialKits.tsx:37` calls `GET /api/iot-enhanced/material-kits` → repo queries `mm_material_kits` (MISSING) → runtime crash
  - `WarehouseMaterialKits.tsx:46` calls `POST /api/iot-enhanced/orders/:id/calculate-bom` → queries `mm_material_kit_items` (MISSING)
  - `WarehouseMaterialKits.tsx:60` calls `PATCH /api/iot/material-kits/:id/prepare` → UPDATE on `mm_material_kits` (MISSING)
  - `WarehouseMaterialKits.tsx:69` calls `PATCH /api/iot/material-kits/:id/ready` → UPDATE on `mm_material_kits` (MISSING)
  - `WarehouseMaterialKits.tsx:80` calls `GET /api/iot-enhanced/material-kits/:id/items` → queries `mm_material_kit_items` (MISSING)

- **Schema column mismatch between FE type and DB table:**
  - FE `MaterialKit` type (`WarehouseMaterialKitsTypes.ts:22`) has field `orderId` — DB `material_kits` has `order_id` (integer FK to papka_orders)
  - FE type has `preparedBy: string | null` — DB has `prepared_by: integer`
  - DB `material_kits.order_id` is integer; Drizzle schema (`mm-batch-mgmt.ts:96`) declares `orderId: varchar("order_id")` referencing `papkaOrders.id` (varchar) — type mismatch between schema declaration and DB DDL (DB shows `integer` type)

- **FE `PapkaOrder` type drift:** `WarehouseMaterialKitsTypes.ts:9-20` expects fields `papkaNo`, `zakaz`, `naimenovanie`, `tiraj`, `formatA`, `formatB` on the orders response. The `/api/iot-enhanced/orders-for-kits` route queries `production_orders` (`iot-enhanced.repository.ts:24`) which returns columns `id`, `order_number`, `status`, `created_at` — none of the papka-specific fields exist. FE will render empty strings/undefined for all display fields.

- **`WmsBarcodeController.createMaterialKit` (wms-barcode.controller.ts:137) hardcodes `order_id = 0`** — `0` will likely violate FK constraint when/if an FK is added; a kit created this way is immediately orphaned.

- **DUPLICATE concept at /api/iot/material-kits vs /api/iot-enhanced/material-kits vs /api/warehouse/material-kits:** Three separate controller prefixes serve "material kits", each targeting different tables. No shared service — all three are independent stacks pointing at different (or missing) tables.

- **`IotEnhancedController.getOrders` (iot-enhanced.controller.ts:128) bypasses Result pattern:** Uses bare `db.execute()` and manual `(r as { rows?: unknown[] }).rows` cast without Result<T> wrapper — violates Qoida 1 and Qoida 16.

- **`getMaterialKitById` in service (iot-enhanced.service.ts:42-46) double-wraps:** `safeCall` wraps `repo.getMaterialKitById` which already returns `Result<Row|null>` — the inner Result is returned as the `data` payload of the outer safeCall, not unwrapped.

### 3-line summary

The FE page `WarehouseMaterialKits.tsx` calls `/api/iot-enhanced/material-kits*` and `/api/iot/material-kits*` which route through `IotEnhancedRepository` that hard-codes queries against `mm_material_kits` and `mm_material_kit_items` — two tables that **do not exist** in the live database, making every kit read/write/prepare/ready action a guaranteed 500 crash.
The canonical tables (`material_kits` / `material_kit_items`) do exist in the DB (Drizzle schema `lib/db/src/schema/mm-batch-mgmt.ts:93`) and have a working CRUD controller at `/api/warehouse/material-kits`, but the FE never calls that prefix.
Fix requires: (1) delete or redirect `iot-enhanced` + `iot` kit routes to point at the canonical `material_kits` table, (2) re-align `IotEnhancedRepository` SQL to use canonical column names (`order_id`, not `production_order_id`), and (3) fix FE `PapkaOrder` field mapping to match what `production_orders` actually returns.
