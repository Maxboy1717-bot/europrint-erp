### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **Two-worlds: GET /design/orders vs GET /design** — Two parallel list routes: `GET /design` (DesignController via CQRS → DrizzleDesignRepository, returns paginated DesignOrder domain objects) and `GET /design/orders` (DesignExtendedController → DesignExtendedRepository.findOrdersList, returns flat rows with nested `{order:{...}}` wrapper). Both read design_orders. FE pages use different paths: DesignOrders.tsx:80 and AIDesignGenerator.tsx:39 hit `/api/design/orders`; DesignDashboard.tsx:66 hits `/api/design/statistics` (different endpoint). The two list routes return incompatible shapes.

- **501-STUB with active FE caller** — `POST /design/orders` (design.controller.ts:218) throws `NotImplementedException`. FE DesignOrders.tsx:84 calls `POST /api/design/orders` — every "New Order" form submit fails with 501. The canonical create path is `POST /design` (requestDesign), but FE does not call it.

- **FE-BE URL mismatch: POST /design/orders** — DesignOrders.tsx:84 `apiRequest('POST', '/api/design/orders', data)` → 501 stub. Canonical BE create is `POST /api/design` (design.controller.ts:112). No FE page calls `POST /api/design`.

- **Broken INSERT — designOrderMessages senderRole NOT NULL** — design.controller.ts:241-245: INSERT omits `senderRole` column. Live schema has `senderRole VARCHAR NOT NULL` with no default. Every `POST /design/orders/:id/messages` will throw PostgreSQL error 23502 (not-null constraint). FE DesignOrderDetail.tsx:79 calls this endpoint.

- **GREEN-LIE: GET /design/templates** — design-extended.repository.ts:68-76 returns 5 hardcoded strings, never queries `brand_templates` table (0 rows, exists). FE AIDesignGenerator.tsx:40 and DesignExtended.tsx:39 consume this endpoint expecting real templates.

- **GREEN-LIE: POST /design/:id/verify** — design-extended.repository.ts:99 returns `Math.random()` scores. No AI integration, no DB persistence. FE AIDesignGenerator.tsx:80 calls this expecting real QC analysis.

- **GREEN-LIE: POST /design/:id/mockup** — design-extended.repository.ts:103 returns a fabricated path `/mockups/${id}-${type}.png`. No actual image generation or storage. FE AIDesignGenerator.tsx:104 calls this.

- **ORPHAN: designOrderNotifications — no writer** — Table exists (0 rows). Only reference is `SELECT * FROM "designOrderNotifications"` in design.controller.ts:162. No INSERT exists in the entire codebase. FE DesignNotifications.tsx:37 queries `/api/design/notifications` and will always get empty results.

- **ORPHAN: design_tooling — no writer** — Table exists (0 rows). Only reads: design.controller.ts:182 (list) and design.controller.ts:199 (wear-forecast). No INSERT or update endpoint. FE AIDesignGeneratorPanels.tsx:140-147 fetches tooling and wear-forecast but data can never be populated.

- **ORPHAN: design_order_revisions — no writer** — Table exists (0 rows). Only a SELECT in design-extended.repository.ts:43. No revision is ever created when status changes in UpdateDesignStatusHandler.

- **ORPHAN: design_comments — no controller** — Table defined in lib/db schema (pp-design.ts:196), exists in live DB (0 rows), but no controller, service, or repository method references it.

- **ORPHAN: brand_templates — no writer, ignored by templates endpoint** — Table exists (0 rows). findTemplates() never queries it; returns hardcoded list. No INSERT path.

- **DUPLICATE list surface** — `GET /design/orders` (DesignExtendedController) and `GET /design` (DesignController) both list design_orders but with different shapes and different repo implementations. DrizzleDesignOrdersSvcRepository (orders/) is a third reader of the same table, used by OrdersService which is exported from DesignModule but has no registered controller route.

- **DUPLICATE: markNotificationRead targets wrong table** — PATCH `/design/notifications/:id/read` calls `execNotificationMarkRead(parseInt(id))` which updates the generic `notifications` table (36 rows), not `designOrderNotifications`. FE DesignNotifications.tsx:48 expects design-specific notification to be marked.

- **design_tooling: die_cut type present but no vision logic** — Schema (pp-design.ts:241) includes `die_cut` as a valid `tooling_type`. Vision #9 (Tigel/die-cut) requires tracking which orders used a tigel and the resulting brak flow. No order-to-tooling link column exists in design_orders or ow_* tables; `design_tooling` has no FK to design_orders; no usage increment writer exists.

- **Qoida 6 violation in DesignController** — design.controller.ts:182-204 performs raw SQL with computed `CASE WHEN` expression and `GREATEST` directly in the controller, bypassing repository pattern.

### 3-line summary

The design slice has real DB-backed routes for create/update/list/statistics on `design_orders` and `designs`, but three core tables are orphans with no writers: `design_tooling` (0 rows, no INSERT route), `designOrderNotifications` (0 rows, no producer), and `design_order_revisions` (0 rows, never written on status change).
