### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **GREEN-LIE (critical): `GET /qc/spc/control-chart` (qc-new.controller.ts:105)** — `getSpcChartData()` in qc-new.repository.ts:191 returns `processCapability:{cp:1.33,cpk:1.21,status:'capable'}` as **hardcoded literals** regardless of actual data. The FE `QCSPCTab.tsx:50` consumes this endpoint and displays Cp/Cpk values to QC engineers. This is a silent lie: values 1.33/1.21 will appear even when the process is out of control.

- **GREEN-LIE: `GET /qc/tests/:id` (qc-parameters.controller.ts:118-124)** — Returns `{id,results:[],passed:null,testedAt:null}` unconditionally with no DB lookup. Code comment says "Service-level findById helper pending."

- **FE<->BE shape mismatch: `/qc/spc/control-chart`** — FE `QCSPCTab.tsx:15-46` expects `ControlChartData` with `dataPoints[], controlLimits:{ucl,lcl,cl,sigma}, outOfControl[], processCapability:{cp,cpk,sigma,interpretation}, weeklyStats[], summary:{n,mean,sigma,...}`. BE returns `{points:Row[], processCapability:{cp,cpk,status}}`. Fields `dataPoints`, `controlLimits`, `outOfControl`, `weeklyStats`, `summary` are all missing. The FE guard `if (!data || data.dataPoints.length === 0)` (line 62) will render "no data" forever even if DB had rows.

- **SPC formula bug — `isCapable` uses Cp not Cpk** (spc.service.ts:179): `isCapable: cp >= CP_CAPABLE` tests the wrong index. Industry standard (ISO 7870-2, AIAG SPC manual) defines a process as capable when **Cpk ≥ 1.33**, not Cp ≥ 1.33. A process centered at the spec edge (Cpk = 0.2) with narrow spread (Cp = 2.0) would be incorrectly reported as "capable" and "excellent". The comment on line 36 ("Cp measures spread; Cpk measures spread AND centering") acknowledges this distinction but the code ignores it. Fix: `isCapable: cpk >= CP_CAPABLE` and `isExcellent: cpk >= CP_EXCELLENT`.

- **ORPHAN: `control_chart_point` table** — Defined in schema-qc-spc.ts:26, exists in live DB (0 rows), but no INSERT exists anywhere in the codebase. `DefectDetectorService.computePChart` (defect-detector.service.ts:31) computes p-chart results entirely in-memory and discards them. The table was created for TZ-D11 p-chart persistence but the write path was never implemented.

- **ORPHAN write path: `qc_spc_data`** — Only read by GET routes; no route or service persists new measurement values. SPC computations in `SpcService.getControlChart` and the `GET /qc/control-charts` route read from this table but there is no POST to populate it. The table is effectively read-only with 0 rows.

- **Two-worlds: SPC data vs p-chart data** — Two separate tables serve overlapping SPC purposes: `qc_spc_data` (continuous X-bar/R measurements, used by `SpcService.getControlChart` via `DrizzleQcComputeRepository.findSpcReadings`) and `control_chart_point` (p-chart attribute samples for `DefectDetectorService.computePChart`, but never read or written at runtime). Neither table has any data. The routes reading from each table are different endpoints with different computation paths.

- **No POST route to submit SPC measurement data** — There is no endpoint for a QC operator to submit a new measurement (value + parameter_id) to `qc_spc_data`. The GET routes can aggregate but there is nothing to aggregate. This is a complete missing write path for the SPC feature.

- **`qc-new.controller.ts:117` direct `db.execute`** — `GET /qc/control-charts` calls `db` directly in the controller body (controller-layer DB access, violating Rule 15). The raw SQL at line 117-128 bypasses the service/repository pattern.

- **`ai-trend` prediction is hardcoded** — `QcNewService.getAiTrend()` (qc-new.service.ts:41-43) appends a static prediction `{nextWeekRisk:'medium',confidenceScore:0.72,recommendation:'...''}` — not derived from data. The trend data itself is real DB queries but the AI prediction is a constant.

### Vision link (which of 22 visions this serves, % built)

Serves **Quality Control / TZ-30 (X-bar/R Control Charts + Process Capability)** and **TZ-D11 (p-chart + Western Electric rules)**. The SPC math layer (`SpcService`, `DefectDetectorService`) is correctly implemented (~80% of domain logic), but the data pipeline to feed it is 0%: no write route to populate `qc_spc_data`, no persistence for p-chart points to `control_chart_point`, and the only SPC route consumed by the FE (`/qc/spc/control-chart`) returns a hardcoded Cp/Cpk rather than computed values. Overall built: ~15% of the SPC vision (schema + domain math exist; data flow, persistence, and correct FE contract all missing).

### 3-line summary

The SPC/control-chart slice has correct Shewhart math in `SpcService` and valid p-chart Western Electric rules in `DefectDetectorService`, but both compute against empty tables (`qc_spc_data` 0 rows, `control_chart_point` 0 rows) because no write endpoint exists. The primary FE-facing route (`GET /qc/spc/control-chart`) is a green-lie: it returns hardcoded `Cp=1.33 / Cpk=1.21` regardless of actual process data, and its response shape is incompatible with `QCSPCTab.tsx` so the tab always renders "no data". The `computeCapability` function also has a formula error: it uses `cp >= 1.33` for `isCapable` instead of the correct `cpk >= 1.33`.
