### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **TWO-WORLDS routing (CRITICAL):** FE `RoutingConfiguration.tsx` calls `/api/erp/routings` + `/api/erp/routing-operations` (erp-products.controller.ts:203); FE `lib/api/pp.ts:22` calls `/api/pp/routing/:id` (pp-routing.controller). Both point to the same `routings` + `routing_operations` tables but via completely separate service/repo stacks. The erp-products path does a hard DELETE; the pp-routing path does a soft-delete (is_active=false). No cross-path consistency.

- **TWO-WORLDS work_centers:** FE `ERPWorkCentersTab.tsx` writes via `/api/erp/work-centers`; FE `MESWorkCenters.tsx` creates via `ppApi.createWorkCenter` → `/api/pp/work-centers`. Both write to the same physical `work_centers` table but through different repos (ErpExtraRepository vs DrizzlePpWorkCentersRepository / DrizzleWorkCenterRepository). Three separate Drizzle bindings exist for the same table: `workCenters` (schema-compat-3.ts), `ppWorkCenters` (schema-pp.ts mapped to `work_centers`), and the canonical in `schema-manufacturing.ts`.

- **TWO-WORLDS routing_operations vs pp_routing_operations:** CRP reads `pp_routing_operations` (pp-crp.service.ts:137) while ERP write path inserts into `routing_operations` (erp.repository.ts:183). CRP will always return zero load because its source table (`pp_routing_operations`) has no writer in the ERP entry path. This is the documented "CRP 503 / efficiency_rate" issue but the deeper problem is the split table.

- **GREEN-LIE:** `GET /api/technology/materials/alternatives` (technology.controller.ts:71 → technology.repository.ts:53) returns hardcoded mock data (three fake alternatives with fixed saving percentages) regardless of input. No DB query.

- **501-STUB with FE caller:** `POST /api/technology/cards/generate` (technology.controller.ts:114) throws NotImplementedException; `TechCards.tsx:81` calls this and will get 501. `POST /api/technology/cards/:id/optimize` (technology.controller.ts:130) same; `TechCards.tsx:70` calls it as GET — verb mismatch on top of 501.

- **501-STUB:** `POST /api/pp/routing` (pp-routing.controller.ts:84) is explicit NotImplementedException. FE `lib/api/pp.ts:24` calls this. Comment confirms: deferred until product catalog + work centers seeded.

- **ORPHAN table `pp_routing`:** Table exists in live DB (`pp_routing`, 0 rows) with columns `id, product_id, routing_name, is_active, version, created_at`. No Drizzle schema binding found in code; no INSERT/UPDATE. Not the same as `routings` (different schema). Dead table.

- **ORPHAN table `pp_work_centers`:** Table exists in live DB, 0 rows. `schema-pp.ts` declares `ppWorkCenters` which maps to `'work_centers'` (the canonical table), NOT `'pp_work_centers'`. The `pp_work_centers` table in the DB has no code writer.

- **ORPHAN `mps_periods`:** Table exists, 0 rows, no writer in pp slice — MPS service reads it as primary source but falls back to `production_orders`. Without seeding mps_periods the MPS endpoint returns only what's in production_orders (also 0).

- **Missing `efficiency_rate` on pp_work_centers:** `pp_work_centers` lacks the `efficiency_rate` column (schema shows it absent); `work_centers` has it added via migrations-drift.ts:607 ALTER TABLE. CRP reads `work_centers.efficiency_rate` (pp-crp.service.ts:118) so CRP works on the canonical table — but pp_work_centers is silently stale.

- **FE drift `/api/erp/routings` → BE has no ERP global-prefix guard:** RoutingConfiguration.tsx queries `/api/erp/routings` and `/api/erp/work-centers`; the erp module controllers exist and match. However `/api/pp/routing` (canonical DDD path) is never called by RoutingConfiguration.tsx — the main FE routing page bypasses the DDD stack entirely.

### 3-line summary

The PP routing slice has two competing path sets pointing at the same tables: a DDD stack (`/api/pp/routing`, `/api/pp/work-centers`) used only by `lib/api/pp.ts` and a legacy ERP stack (`/api/erp/routings`, `/api/erp/work-centers`) used by the actual FE routing page (`RoutingConfiguration.tsx`). The DDD stack has POST /api/pp/routing as a 501-stub; the ERP stack performs hard DELETEs vs the DDD stack's soft-deletes. CRP (`/api/pp/crp`) reads `pp_routing_operations` while all ERP writes go to `routing_operations` — guaranteeing CRP always returns zero load. All seven core tables (`work_centers`, `routings`, `routing_operations`, `pp_routing_operations`, `production_orders`, `mps_periods`, `technology_cards`) exist in the DB at 0 rows; two ghost tables (`pp_routing`, `pp_work_centers`) have no code writers; `GET /api/technology/materials/alternatives` is a green-lie (hardcoded mock).
