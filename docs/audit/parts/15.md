### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **THREE-WORLD tech card split**: Three separate tables serve "technology card" concept with no FK or sync between them:
  1. `tech_cards` (7 cols, papka_order_id, print attributes) — no writer, orphan effectively
  2. `technology_cards` (18 cols, AI-generated, `calculated_by_ai`, `operations` text, `product_id`) — no writer; only read by 2 routes
  3. `ow_tech_cards` (11 cols, UUID PK, order-workflow status machine, FK → sales_orders) — canonical for Phase 4 fan-out, has a real writer
  - FE `TechCards.tsx` calls `/api/technology/cards` which reads `technology_cards` (world 2); the Phase 4 design dept uses `ow_tech_cards` (world 3); neither is connected to the other

- **501-STUB + FE caller**: `POST /technology/cards/generate` (technology.controller.ts:114) returns `notImplemented()` but `TechCards.tsx:81` actively calls it to generate AI tech cards. Users see an error on submit.

- **501-STUB + wrong HTTP method**: `POST /technology/cards/:id/optimize` (technology.controller.ts:129) returns `notImplemented()`. FE `TechCards.tsx:70` calls it via `GET` (wrong method, will never match the POST route even if implemented).

- **GREEN-LIE — material alternatives**: `GET /technology/materials/alternatives` (technology.repository.ts:53-67) returns hardcoded mock data (`{name, saving, note}[]`) with no DB access. Always returns the same 3 placeholder rows regardless of input.

- **GREEN-LIE field — dashboard**: `avgProcessingHours` field in `findDashboardStats()` (technology.repository.ts:73) is hardcoded to `4`; never computed from real data.

- **No tech_card → BOM link**: `technology_cards` has `product_id` (integer) but no FK to any BOM table. `boms`/`bom_headers`/`bom_items` all exist but contain 0 rows. No code links a generated tech card to a BOM record — the "Tech card → BOM" vision step is entirely unimplemented.

- **AI generates but does not persist**: `POST /ai-agents/prepress/tech-card` (ai-agents.controller.ts:118) calls Gemini, computes `techCardJson`, logs to `ai_decision_log`, but writes nothing to `technology_cards` or `tech_cards`. Result is ephemeral — only the audit log row is persisted.

- **Duplicate route path**: `GET /technology-cards` (general-legacy-b.controller.ts:196) and `GET /technology/cards` (technology.controller.ts:103) both read from `technology_cards`; different URL prefixes, same table — legacy route should be removed.

- **No Drizzle schema for technology_cards**: `technology_cards` is used via raw `db.execute(sql\`...\`)` (technology.repository.ts:87,94) because no pgTable definition exists in `@shared/db` for it. The comment at legacy-iot.service.ts:130 confirms this: "no pgTable definition found for `technology_cards`". This means type safety and migration coverage are missing.

- **papka_orders two-schema conflict**: `queries-technology.ts:13-18` documents a "TODO PA-SCHEMA" — `papka_orders_tech` re-export points to messaging schema (schema-business-c-1.ts), not the print-orders schema. All tech-order queries bypass Drizzle ORM entirely and use raw SQL as a workaround.

- **TechThreeCheckpointEvent never published**: `tech-three-checkpoint.listener.ts` (the listener for the 3-checkpoint → advance-check pipeline) states explicitly at line 21: "No production code currently publishes this event on the CQRS bus." `approveOrder` in technology.controller.ts updates `technology_approvals` but never emits `TechThreeCheckpointEvent` — the downstream advance-approved fan-out is dead-letter.

### 3-line summary

The technology-cards slice has three parallel tables (`tech_cards`, `technology_cards`, `ow_tech_cards`) with no FK or sync — only `ow_tech_cards` has a real writer (Phase 4 fan-out). The AI-generation endpoint (`POST /ai-agents/prepress/tech-card`) calls Gemini and logs to `ai_decision_log` but never persists the result into any tech-card table; the UI-facing generate route (`POST /technology/cards/generate`) is a 501 stub. The critical BOM link from tech card is entirely absent, and the 3-checkpoint→advance pipeline event (`TechThreeCheckpointEvent`) is never published, leaving the downstream advance-approval flow dead-letter.
