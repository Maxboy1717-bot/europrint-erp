### Breaks (drift / missing FK / two-worlds / green-lie / orphan)

- **Two-worlds (material master):** FE `WMSMaterials.tsx` calls `GET /api/inventory/materials` → BE reads `mm_materials` (0 rows, no writer). Canonical table is `material_cards` (21 rows, 4 writers). A second parallel world `materials` (0 rows) is used by `GET /api/mm/materials`. Three representations of material master with no cross-writes. `inventory-materials.repository.ts:21-26`.

- **501-STUB blocks create:** FE `MaterialDialog.tsx:73` calls `POST /api/inventory/materials` → BE throws `NotImplementedException` (`inventory-materials.controller.ts:118`). Users see a dialog but can never create. The correct writer path exists at `POST /api/warehouse/materials` (warehouse-catalog.controller.ts) which writes to `material_cards`.

- **Response-shape drift (silent empty list):** Controller `listMaterials` returns `{ items, total, page, limit }` (`inventory-materials.controller.ts:68-69`). FE reads `data?.data || []` (`WMSMaterials.tsx:112`). Field `data` is not in the BE response → FE always renders empty table even if mm_materials had rows.

- **Missing table: mm_purchase_order_lines:** `getMaterialRecentPurchases` at `inventory-materials.repository.ts:62` queries `mm_purchase_order_lines pol JOIN mm_purchase_orders po ...`. The table `mm_purchase_order_lines` does NOT exist in the live DB (confirmed via information_schema). Actual table is `mm_purchase_order_items`. Any call to `/api/inventory/materials/:id/360-card` that reaches the purchases branch will crash with a PostgreSQL relation-does-not-exist error.

- **Missing column: wms_transactions.deleted_at:** `getMaterialRecentTransactions` at `inventory-materials.repository.ts:70` filters `WHERE t.deleted_at IS NULL`. Column `deleted_at` does not exist on `wms_transactions` (confirmed via information_schema). This query will throw at runtime if `wms_transactions` has any rows.

- **Writes to wrong table:** PUT `/api/inventory/materials/:id` and DELETE `/api/inventory/materials/:id` target `mm_materials` (0 rows, no writer, non-canonical). Actual material data lives in `material_cards`. Edits to the UI would update a ghost table, never touching the real data.

- **Orphan endpoint: inventory/advanced/barcodes:** `inventory_barcode_assignments` table has 0 rows and no writer in the codebase. `GET /api/inventory/advanced/barcodes` always returns empty.

- **No FE consumer for /inventory/advanced:** No FE page or hook calls any `/api/inventory/advanced/*` route. The entire `InventoryAdvancedController` is back-end only with no FE surface — no user can reach it via the UI.

### 3-line summary

The `inventory-materials` slice has a critical three-way "material worlds" split: the FE list calls `/api/inventory/materials` which reads `mm_materials` (0 rows, no writer), the canonical data sits in `material_cards` (21 rows, 4 writers), and a third empty `materials` table is used by the mm-module. The create endpoint (`POST /api/inventory/materials`) is a hard 501 stub, the 360-card crashes on a nonexistent `mm_purchase_order_lines` table, the response shape mismatches so the list always renders empty, and update/delete target the wrong (empty) table. The `inventory-advanced` sub-slice correctly queries `inventory_counts` (6 rows) but has zero FE callers.
