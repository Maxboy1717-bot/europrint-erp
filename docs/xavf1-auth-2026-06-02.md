## 4. JWT XAVFSIZLIGI

### Konfiguratsiya

| Parametr | Holat | Izoh |
|---|---|---|
| JWT_SECRET manbai | `.env` fayldan — **xavfsiz** | `config/jwt.config.ts:9-10` — `.env` yo'q bo'lsa server FATAL xato beradi |
| JWT_REFRESH_SECRET | `.env` fayldan — **alohida** | Refresh token uchun boshqa kalit — to'g'ri |
| Access token TTL | `24h` (kodda hardcoded) | `login.service.ts:192` — `jwt.config.ts` default: `8h`, lekin `login.service.ts` `24h` qo'llaydi |
| Refresh token TTL | `7d` | Oqilona |
| Algoritm | `HS256` (config da belgilangan) | `jwt.config.ts:20` — lekin `jwtService.verify()` da `algorithms:` option BERILMAGAN |
| Algoritm pinning | **YO'Q** (`verify()` da) | JwtAuthGuard va auth.controller.ts `verify()` chaqirishlarida `algorithms: ['HS256']` ko'rsatilmagan |
| Cookie security | `httpOnly: true`, `sameSite: 'strict'`, `secure: true` (production) | **To'g'ri** |
| JTI blacklist | Mavjud (refresh_tokens jadvalida) | DB xato bo'lsa **fail-open** — token bekor bo'lmaydi |
| Refresh token | Mavjud (`JWT_REFRESH_SECRET` bilan) | **To'g'ri** |
| Token tanasi | `sub, username, email, role, jti` | `positionId` token ichida **YO'Q** (PermissionGuard `positionId`ni `request.user`dan oladi) |

### TTL ziddiyati (xavf: MEDIUM)

`login.service.ts:192` → `expiresIn: '24h'` (hardcoded)
`auth.module.ts:43` → `JWT_ACCESS_TOKEN_TTL ?? JWT_EXPIRES_IN ?? '24h'`
`jwt.config.ts:17` → `JWT_EXPIRES_IN || '8h'`
`auth.controller.ts:173` → `JWT_EXPIRES_IN ?? '24h'`

Har xil joyda har xil default — admin refresh orqali 24h, lekin config orqali 8h chiqishi mumkin. `.env`da `JWT_EXPIRES_IN` belgilanmasa farq paydo bo'ladi.

### Algoritm pinning yo'qligi (xavf: LOW-MEDIUM)

`JwtAuthGuard.canActivate()` → `this.jwtService.verify(token)` — `algorithms` option yo'q.
`auth.controller.ts:164` → `this.jwtService.verify(oldRefreshToken, { secret: refreshSecret })` — `algorithms` yo'q.

Agar JWT_SECRET almashtirilib RS256 key bo'lsa (ehtimoli past), "algorithm confusion" hujumi nazariy mumkin. Amalda muammo emas, lekin best practice — `{ algorithms: ['HS256'] }` qo'shish.

## 5. PIN/IMZO XAVFSIZLIGI

### Parol hashing

| Komponent | Usul | Narx (cost) | Fayl |
|---|---|---|---|
| Barcha parol hashlash | `bcrypt` | **12 rounds** | `common/constants/security.constants.ts:BCRYPT_ROUNDS=12` |
| Admin seed | `bcrypt.hash(pass, BCRYPT_ROUNDS)` | 12 | `database/seeds/admin.seed.ts` |
| Foydalanuvchi yaratish | `bcrypt.hash(pass, BCRYPT_ROUNDS)` | 12 | `admin/application/services/create-user.service.ts` |

**12 rounds** — industry standart (OWASP 2024 tavsiyasi: minimum 10, ideal 12-14). **Yaxshi.**

### PIN xavfsizligi

- `common/constants/security.constants.ts` komentariyasida "ALL password / PIN hashing" deyilgan — PIN ham bcrypt bilan
- `generated/i18n.generated.ts` da `pinLengthInvalid`, `pinNotSet`, `pinIncorrect` kalit so'zlari bor
- Aisha VA yordamchisi uchun `requiresPIN: boolean` VO mavjud (critical amallar uchun)
- POS kassir PIN hashing: bevosita ko'rib chiqilmadi, lekin `BCRYPT_ROUNDS` kanon sifatida import qilinadi

**Xulosa:** Hashing infrastrukturasi to'g'ri qurilgan.

## 6. SEPARATION OF DUTIES (SoD)

### SodGuard holati

**Ulangan:** global APP_GUARD sifatida (app.module.ts:196)

### Tekshiriladigan SoD qoidalar

| Qoida | Trigger | Tekshiruv |
|---|---|---|
| 1. PO yaratish + tasdiqlash | `/purchase-order` POST yoki `/purchase-order/approve` PUT | `po:create` VA `po:approve` bir kishida bo'lsa — BLOCK |
| 2. Invoice + to'lov | `/invoice` POST yoki `/payment/approve` PUT | `invoice:create` VA `payment:approve` — BLOCK |
| 3. Ombor qabul + chiqim | `/warehouse/receive` yoki `/warehouse/issue` POST | `warehouse:receive` VA `warehouse:issue` — BLOCK |
| 4. Ish haqi hisoblash + tasdiqlash | `/payroll/calculate` POST yoki `/payroll/approve` PUT | `payroll:calculate` VA `payroll:approve` — BLOCK |
| 5. Material yaratish + o'chirish | `/mm/materials` yoki `/materials` POST/DELETE | `material:create` VA `material:delete` — BLOCK |
| 6. CRM RFM + Churn (strict) | `/crm/rfm/cluster` yoki `/crm/churn/retrain` POST | Ikkalasi bir foydalanuvchida — BLOCK |

### Zaifligi: path-based trigger

SodGuard URL path orqali ishlaydi. Masalan, qoida 1 faqat literal `/purchase-order` va `/purchase-order/approve` yo'llarini tekshiradi. Agar endpoint nomlanishi o'zgarsa (masalan `/po/` yoki `/procurement/`) — SoD tekshiruvi o'tkazib yuboriladi. Bu architectural risk.

**Bir kishi PO yaratib + tasdiqlashi mumkinmi?**
Agar foydalanuvchida `po:create` VA `po:approve` ruxsatlari bo'lsa — `SodGuard` bloklaydi. Ruxsatlar `positionPermissions` jadvalidan keladi. Amalda PermissionGuard ham ishlaydi — agar ruxsat berilmagan bo'lsa avvalroq bloklangan bo'lardi.

## 9. XULOSA

**Umumiy xavf darajasi:** LOW (asosiy blocker tuzatilgan)

Tizimning auth/authz infrastrukturasi yaxshi qurilgan: 5 qatlamli global guard (throttler + JWT + roles + SoD + permission), bcrypt 12, httpOnly cookie, alohida refresh secret, account lockout. Avvalgi auditda topilgan 2 ta High zaiflik (IoT planshet, storage) tuzatilgan va tasdiqlangan.

**Qolgan eng muhim harakatlar:**
1. **P1 (ishga tushishdan oldin):** Production JWT secret almashtirish (hozir `local-dev-*` placeholder)
2. **P1:** OTP per-session urinish limiti qo'shish (`otp_sessions.attempts` ustuni)
3. **P2:** `pip` va `enps` controllerlariga `@Roles` qo'shish (HR_MANAGER yoki SUPER_ADMIN)
4. **P3:** JWT verify chaqirishlarida `algorithms: ['HS256']` pinlash
5. **P3:** Token TTL ziddiyatini bir joyga jamlashtirish (`JWT_ACCESS_TOKEN_TTL` .env o'zgaruvchisi)
